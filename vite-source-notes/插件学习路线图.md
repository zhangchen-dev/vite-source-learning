### 6 个职责域速览

| 域 | 核心职责 | 代表插件 | 优先级 |
|----|----------|----------|--------|
| **模块定位域** | import 字符串 → 绝对路径 | preAlias → alias → **oxcResolvePlugin** | 🔴 必须读 |
| **资源/文件域** | 非 JS 文件处理 | css → asset → json → wasm → worker | 🔴 必须读 |
| **预处理器域** | 源码 AST 变换 | oxc → **define** (已读) | 🟡 选读 |
| **构建增强域** | build 时额外产物 | buildHtml → importGlob → dynamicImportVars | 🟡 选读 |
| **依赖优化域** (dev) | 预打包第三方依赖 | optimizedDeps | 🟢 跳过 |
| **Server/Dev 域** (dev) | HMR + dev 服务器重写 | **importAnalysis** → clientInjections | 🔴 必须读 |

## 三、每个阶段的学习目标 + 时间预估

### 🔴 第一阶段：resolve 插件（30 分钟）

**为什么排在 define + asset 之后？**

define 只管 transform，asset 只管特定资源。你现在知道了"模块处理三步曲"（resolveId → load → transform），但**绝大多数 import 的 resolve 链路在 resolve 插件里**，asset 的 resolveId 只是拦截特例。读完 resolve 你才能把"模块定位"这条主线串起来。

**学习重点：**

```
import 'lodash'
    ↓ resolveId（resolve 插件）
    ↓ 查 package.json 的 main/module/exports 字段
    ↓ 拼出 node_modules/lodash/index.js 的绝对路径
    ↓ return { id: 'D:/project/node_modules/lodash/index.js' }
    ↓ Rolldown 继续给下一个插件的 load 钩子
```

**看什么：**
- `oxcResolvePlugin` 返回的 `resolveId` 钩子 —— 核心就是这一个钩子
- 它的 filter 配置 —— 理解它"什么都接"（没有 filter，所有 import 都过它）
- `legacyInconsistentCjsInterop` 参数 —— 可选读，理解历史兼容

**跳过什么：**
- CJS/ESM interop 兼容代码（长段 try-catch）
- `asSrc: true` 和 `optimizeDeps` 参数的深层细节
- Rolldown 原生 resolve 的 Rust 实现（看不到 JS 源码）

---

### 🔴 第二阶段：preAlias 插件（10 分钟）

**为什么在 resolve 之前？**

alias 替换路径有个顺序：preAlias（Vite 内置，在 resolve 前改路径前缀）→ aliasPlugin（用户配置的 resolve.alias）→ oxcResolvePlugin（真正去文件系统找）。

**学习重点：**
- 什么时候需要 preAlias？—— 比如 `@fs/` 前缀、`/@id/` 前缀的转换
- 它是怎么和后面的 resolveId 链配合的？

---

### 🔴 第三阶段：importAnalysis 插件（dev）（25 分钟）

**为什么是 dev 专属核心？**

你之前多次看到 `isBundled` / `config.command === 'build'` 这种 if-else 判断。读完 asset 知道了 build 时的 emitFile + resolveFileUrl 链路。但 **dev 时根本不走打包**，dev 服务器是个"源码重写器"——importAnalysis 就是 dev 重写的核心引擎。

**dev vs build 的本质差异：**

```
dev 模式（isBundled = false）
  importAnalysis 插件 transform 所有 JS：
    - 注入 import '/@vite/client'（HMR runtime）
    - bare import 'lodash' → '/@id/lodash'（让 dev server 能拦截）
    - CSS import → 注入 HMR 更新监听

build 模式（isBundled = true）
  importAnalysisBuild 插件：
    - 什么都不做
    - Rolldown 原生处理所有模块关系
```

**学习重点：**
- `transform` 钩子做了哪些字符串替换（`/@id/` 前缀、HMR client 注入）
- 为什么 dev 不需要 `resolveFileUrl`（asset 里的 referenceId 路径）
- `clientInjectionsPlugin` 和它的关系（都注入了 vite client，分工不同）

---

### 🔴 第四阶段：importAnalysisBuild / css + html（20 分钟）

**为什么排第四？**

读完 importAnalysis（dev），你自然想知道 build 时为什么不需要这些重写。同时 css/html 插件能帮你理解 asset 插件里 `renderChunk` 处理 `__VITE_ASSET__` 的完整场景。

**学习重点：**
- css 插件：CSS 转译到 JS 时怎么处理资源引用？→ 生成 `__VITE_ASSET__xxx__`
- cssPost 插件：`resolveFileUrl` 钩子处理 CSS 场景的 asset URL
- buildHtmlPlugin：build 时怎么处理 HTML 里的 `<link>` / `<script>`

---

### 🟡 第五阶段：按需选读（每个 10 分钟）

以下插件每个都很小、职责单一，根据需要选读：

| 插件 | 什么时候读 | 学什么 |
|------|-----------|--------|
| json 插件 | 想知道 `import data from './data.json'` 怎么来的 | load + transform，一行代码的小插件 |
| wasm 插件 | 遇到 `import wasm from './foo.wasm?init'` | resolveId + load 生成初始化 JS |
| workerImportMetaUrl | 想理解 asset 里 resolveFileUrl 的 asFileUrl 分支 | resolveFileUrl 钩子处理 Worker URL |
| dynamicImportVars | 用到 `import.meta.glob('./locales/*.json')` | transform 里 glob 展开 |
| importGlob | 同上 | transform + generateBundle |

### 🟢 跳过清单（工具层，不影响理解 Vite 核心）

| 插件 | 为什么跳过 |
|------|-----------|

## 四、推荐的实际阅读动作

每读一个插件，按这个 SOP 来：

```
Step 1：扫一眼插件返回的对象结构
         → 知道它实现了哪些钩子
         → 结合 plugins/index.ts 的注册顺序，知道它在链路中的位置

Step 2：找到它的 filter 配置（如果用 Rolldown 新格式）
         → 知道它"关心什么类型的模块"

Step 3：看每个钩子的 handler
         → 只看核心逻辑，跳过边界条件/错误处理
         → 用具体例子走一遍数据流

Step 4：和已经读过的插件做对比
         → 这个钩子和 define/asset 的同名钩子有什么不同？
         → 它和 asset 插件有什么联动？

Step 5：看完后用"一句话总结"写在笔记里
```

## 五、里程碑检查点

读完所有 🔴 插件后，你应该能回答这些问题（不需要翻源码）：

- [ ] `import 'lodash'` 在 dev 下怎么被 dev server 找到的？在 build 下怎么被 Rolldown 打包的？
- [ ] asset 插件的 `resolveFileUrl` 和 cssPost 插件的 `resolveFileUrl` 有什么关系？为什么两个插件都要实现同一个钩子？
- [ ] dev 时为什么 importAnalysis 要给 bare import 加 `/@id/` 前缀？
- [ ] build 时 `__VITE_ASSET__xxx__` 和 `import.meta.ROLLDOWN_FILE_URL_*` 两种占位符分别在什么场景生成、什么场景被替换？
- [ ] resolveFileUrl 里的 `chunkId` 参数传给 `toOutputFilePathInJS` 是用来干什么的？（提示：base 为 './' 时要算相对路径，得知道"当前 chunk 在哪"）
